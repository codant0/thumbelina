RAG学习

原理：
1. **知识向量化**：本地知识向量化存储，用以后续相似度搜索，需要使用向量数据库
2. **语义召回**：用户检索时，根据相似度搜索，从向量数据库中召回相关片段
3. **上下文整合**：根据提示词整合召回片段，发送给LLM

整体即：
* 准备部分（提问前）：分片 -> 索引
* 回答部分（提问后）：召回 -> 重排 -> 生成

一般的分块策略为：递归字符串分割、chunk size 512 toens、overlap 50~100 tokens



# 前置工作
文档预处理是容易忽略的一个最有效的潜质环节
## 文件去重

企业内部文档中，同一个文件可能会出现多个版本，导致：

1. 向量库中出现大量重复的chunk
2. 检索结果重复，召回率和召回精度都可能受到挤压而降低
3. 浪费存储和向量化计算资源

RAG去重通常分为多个维度：

* 文档级去重：最常用的，从源头控制数据质量。防止重复文档入库，节省存储和计算资源
* 分块级去重：分块后，通过内容、语义等方向，过滤同一意思不同表述的分块。消除chunk内部的语义重复，提升索引质量
* 检索级去重：即使经过文档级、分块级去重后，仍可能在检索时返回重复内容。该步骤保证送入生成模型的上下文信息不重复、不冗余



由于知识库数据量可能极大，因此在判断文件重复时，可以考虑使用多层漏斗的方式进行去重。如：

``` text
文件输入
⬇️
【第一层：精确去重】（耗时：微妙级）
⬇️完全匹配则丢弃，未命中则进入下一级
【第二层：粗筛】（耗时：毫秒级，针对长文本筛选）
⬇️SimHash粗筛，比较文档是否与历史文档相近，判断是丢弃、覆盖（删除原document）、还是进入chunk筛选
【第三层：精筛】（耗时，秒级，仅针对极少数边界模糊的候选，这里一般就是分块级去重了，可以不考虑）
⬇️根据编辑距离判断是否丢弃
【入库】存储sha256指纹、SimHash指纹
```



### 文档级去重策略

* **精确去重**
  判断上传文件与历史文件是否完全相同，一般使用MD5或SHA-256。快速过滤（微妙级），无法判断相似文件

  * MD5
  * SHA-256

  由于MD5存在极小概率碰撞，且对于文件处理二者性能上差距极低，因此一般选择SHA-256。

  **处理策略：**对于重复的文档，可以考虑直接忽略

* **粗筛**
  将文档转为指纹，通过汉明距离或Jaccard相似度进行判断，低于阈值则判断近似

  > 汉明距离：两个等长字符串对应位置不同字符的数量。如（以8bit举例）：
  >
  > 字符串A： 1 0 1 1 0 0 1 1
  >
  > 字符串B： 1 0 0 1 0 0 1 0
  >
  > 汉明距离为2，对于8bit的SimHash数据而言，就可以认为是有一定相似性，需要进一步判断（如后续使用Chunk去重）

  * SimHash

  * MinHash

    |            | SimHash                | MinHash                |
    | ---------- | ---------------------- | ---------------------- |
    | 相似度度量 | 汉明距离               | Jaccard相似度          |
    | 空间       | 极小（几字节一个指纹） | 较大（需存多个签名）   |
    | 速度       | 极快，单次遍历生成     | 较快，需多次哈西       |
    | 近似精度   | 适合高频词主导的长文档 | 对短文档和词汇重叠敏感 |
    | 实现复杂度 | 简单                   | 简单                   |
    | 使用场景   | 网页去重、长文档       | 任意长度、通用文本去重 |

  

  比较下来，选择使用SimHash作为文档第二层粗筛的算法

  **处理策略：**以SimHash的汉明距离为例，若使用的是64bit的bit指纹（通常SimHash输出就是64bit或128bit）。汉明距离：

  * =0      => 完全相同，忽略新文档
  * 1~3    => 高度近似，可视为重复，用后续文档覆盖前一文档
  * 4~10  => 有一定相似性，需要进一步判断，考虑后续使用chunk去重
  * \>10    => 基本不同

  需注意：新建文档的simhash值，与海量存量文档比较可能存在性能问题，可考虑如下优化方式：

  1. 依赖数据库插件，如：
     * **PostgreSQL + smlar插件**：该插件让PostgreSQL能够高效地基于海明距离检索海量SimHash数据。只需将SimHash值作为数据类型存入，插件会自动处理索引和查询优化。
     * **sqlite**：**`sqlite-vec`**，这是目前最推荐的扩展，轻量且活跃。它支持将 SimHash 值作为**二进制向量（BLOB）** 存储，并能直接计算**汉明距离（Hamming Distance）**。
     * **其他数据库**：一些新兴的向量数据库（如Milvus）或具有向量搜索功能的传统数据库（如Elasticsearch），也内置或通过插件支持类似LSH的近似最近邻搜索算法，可以作为备选方案。



### 分块级去重

分块后，通过内容、语义等方向，过滤同一意思不同表述的分块。消除chunk内部的语义重复，提升索引质量。

策略举例：

sha256精确去重（精确匹配） ➡️ MinHash近似去重（Jaccard > 0.8~0.9匹配） ➡️ 小模型Embedding语义去重（余弦相似度>0.92~0.98相似）

整体实现方式与文档级去重类似，只是目标的content从document content变成了 chunk content



### 检索级去重

即使写入时做了去重，检索时仍可能返回重复内容：

  - 同一主题的不同文档包含相似 chunk
  - 用户查询的语义相近 chunk 分散在多个文档中
  - 前两层漏网的近似 chunk（阈值设得太严格）

核心思路：检索返回top-k后，对结果本身再做一次去重，再进行rerank或送给大模型。

可以考虑使用SimHash或编辑距离

# 数据准备

1. 数据加载：将各种非结构化文档，转换为程序可用的结构化数据。
2. 数据分块：将加载后的长篇文档，切分成文本块，是后续向量检索和模型处理的基本单位。

流程：
1. 分词：将文本块分为独立的Token
2. 向量化：为每个Token生成一个高维度向量表示
3. 池化：将分块中的所有Token**压缩成一个单一的向量**，这个向量代表整个文本块的语义。
   * case
     * 文本块：大鱼吃小鱼
     * Tokens：[大鱼]、[吃]、[小鱼]
     * 向量化（以三维举例，实际维度巨大）：[0.2, 0.8, 0.1]、[0.6, 0.3, 0.5]、[0.9, 0.1, 0.7]
     * 池化结果（使用最常见的池化方式-平均池化，每个维度相加求平均）：[0.566, 0.400, 0.433]

切块大小？
   * 切块不宜过大：首先不能超过所使用嵌入模型的上下文长度上限，否则超出部分会直接截断，导致信息丢失；检索后需要将取回的多个切块一并放入大模型的窗口中，若单个块过大，则可能只能容纳少数相关块（随着大模型上下文窗口增大，一般影响较小）。
   * 切块不宜过小：切块过小会导致上下文割裂，语义丢失
   * benchmark推荐的默认chunk size为512 tokens，大部分场景都是满足的。但若是如SOP等规程类文档，可以考虑768 tokens，使得文档中的流程完整；对于FAQ类的问答文档，考虑256 tokens就够了，避免将不想管的问题混在一个chunk中。

**标题：**
文档标题、章节标题经常包含了极其重要的信息，可以考虑将文档标题、章节标题作为metadata附加在每个chunk中，检索的时候一起参与匹配。

### PDF加载*

PDF文档可能存在如下类型：

1. 纯文本PDF（使用文本提取库提取）
2. 扫描件PDF（使用OCR引擎提取）
3. 文本+扫描件PDF（组合方案）

对此可用如下策略判断：

1. 字符密度：单页字符较少，可能为扫描件
2. 图片覆盖面积比：大图铺满页面，极可能包含扫描件

``` python
def _classify_page(page) -> PageKind:
    text = page.get_text("text").strip()
    # 信号1：字符密度
    sparse_text = len(text) < 20
    # 信号2：图片覆盖面积占比（扫描件特征：大图铺满页面）
    page_area = page.rect.width * page.rect.height
    img_area = sum(
      (b["bbox"][2] - b["bbox"][0]) * (b["bbox"][3] - b["bbox"][1])
      for b in page.get_image_info()
    )
    image_dominant = img_area > 0.6 * page_area
    # 信号3（可选）：文本层质量——字母/数字占比，识别"有文本层的扫描件"的垃圾文本
    
    
    if sparse_text and image_dominant:
      return PageKind.SCANNED
    if image_dominant and not sparse_text:
      return PageKind.MIXED   # 图文混排，文本可用
    return PageKind.TEXT
```

# 检索优化

## 混合检索
结合稀疏向量和密集向量优势的搜索技术。

**稀疏向量**：也称为“词法向量”，基于词频统计的，维度极高，但大多数元素为0的向量。
* 优点：无需训练、可解释性强，对于**专业术语**和**特定名词**检索效果好
* 缺点：无法理解语义

**密集向量**：也称为“语义向量”，基于深度学习得到的低纬度、连续、充满意义的语义空间。
* 优点：可以理解同义词、近义词以及上下文
* 缺点：可解释性差，向量中的每个维度没有明确的含义，通过大量训练获取

**混合检索**：结合稀疏向量和密集向量的优点。

### 融合方法
常见如下两种融合方式：

**倒数排序融合(Reciprocal Rank Fusion, RRF)**
不关心在检索系统中的原始得分，只关心每个文档在各自结果集中的排名。其思想为：一个文档在不同检索系统中的排名越高，他的最终得分就越高。

**加权线性组合**
将不同检索系统的得分进行归一化，通过权重参数（控制不同系统得分权重）进行线性组合。
通过调整权重参数即可实现语义相似性与关键词匹配在最终结果的权重。
如电商系统中，调高关键词检索的权重；在知识问答系统中，调高语义检索的权重。

两种方法融合的优势：
* 召回率和准确性高：能同时捕捉关键词和语义，显著由于单一检索；
* 灵活性强：可以配置权重以适配不同场景
* 容错性好：向量模型可部分弥补关键词检索对拼写错误或罕见词的敏感性。

劣势：
* 资源开销大：同时维护两套检索系统
* 参数调试复杂：需反复调整权重参数
* 仍无法解决向量检索系统的不可解释性

## 精确排序
对于精排的模型，考虑使用BGE-M3或者更小更新的Qwen-3-Embedding-0.6B；
如BGE-M3搭配bge-reranker-v2-m3做精排——BM25稀疏检索加BGE-M3密集向量双路召回，然后bge-reranker精排。
典型流程：
1. 密集向量检索（依赖向量数据库），得到top50
2. 稀疏向量检索（BM25），得到top50
3. 混合检索（RRF/加权线性组合），得到top80
4. rerankker对query-chunk pair打分（该步骤较慢）
5. 取rerank top5~top10放入大模型的查询提示词中

## query改写
用户问题通常不是检索友好的，可能描述不明确或与知识库中的名词存在差异。
方案：
1. query改写：用大模型把用户的原始问题改写成多个检索的query
2. HyDE：让大模型先根据用户问题生成一个假设性答案，然后用这个假设性答案的向量去做检索。假设性答案在语义空间里更接近知识库中的真实文档，检索效果更好
